# Data model

## Database boundary

Application tables live in a `private` PostgreSQL schema. The Supabase Data API does not expose that schema to the browser. FastAPI connects through a dedicated role with only the grants required by the application.

If implementation places any table in `public`, it must enable row-level security and explicitly restrict `anon` and `authenticated`. A policy that only says `TO authenticated` is insufficient because it does not enforce row ownership.

Supabase Auth remains the source of the authentication identity. Application authorization uses the internal user, device, and session records described below.

## Conventions

- Primary identifiers use UUIDs generated by the server or database.
- Timestamps use `timestamptz` in UTC.
- Email addresses are normalized for lookup but the original form may be kept for display.
- Public keys and hashes use `bytea`, not ad hoc text encodings.
- Status columns use checked text values or database enums.
- Foreign keys and uniqueness constraints enforce account ownership where possible.
- Cleanup operations use indexed expiry columns.

## Tables

### `app_users`

| Column | Purpose |
| --- | --- |
| `id` | Internal account identifier |
| `supabase_user_id` | Unique link to Supabase Auth |
| `email_normalized` | Unique normalized email used for account lookup |
| `device_epoch` | Current device-authorization epoch, retained for explicit future account-wide reset support |
| `created_at` | Account creation time |
| `email_fallback_at` | Most recent email fallback time, nullable |
| `deleted_at` | Soft-delete marker during deletion workflow |

Authorization must not use editable Supabase `user_metadata`. The verified Supabase user identifier and application database relationships establish ownership.

### `devices`

| Column | Purpose |
| --- | --- |
| `id` | Device identifier |
| `user_id` | Owning account |
| `epoch` | Account epoch in which the device was enrolled |
| `label` | User-visible, length-limited plain text |
| `signing_public_key_spki` | ECDSA P-256 public key |
| `fingerprint` | Unique SHA-256 fingerprint |
| `status` | `active`, `inactive`, or `revoked` |
| `created_at` | Enrollment time |
| `last_seen_at` | Coarse activity time |
| `revoked_at` | Revocation time, nullable |
| `linked_by_device_id` | Device that generated the linking OTP, nullable for email fallback |

The fingerprint is unique within an account. Devices with `status = active` can authenticate and transfer. Logging a device out changes it to `inactive` without deleting its key record; a later device-key challenge or verified email fallback can reactivate it. Revoked devices cannot reactivate without a new enrollment. Authorization also requires `epoch = app_users.device_epoch`.

### `app_sessions`

| Column | Purpose |
| --- | --- |
| `id` | Session record identifier |
| `user_id` | Owning account |
| `device_id` | Associated trusted device |
| `token_hash` | Unique SHA-256 hash of the cookie token |
| `csrf_hash` | Hash of the session-bound CSRF secret |
| `epoch` | Account epoch at issue time |
| `created_at` | Issue time |
| `last_seen_at` | Last accepted use, updated at a bounded frequency |
| `idle_expires_at` | Sliding idle expiry |
| `absolute_expires_at` | Non-sliding maximum expiry |
| `revoked_at` | Revocation time, nullable |
| `revocation_reason` | Enumerated reason, nullable |

Raw session and CSRF values never enter the database or logs. Session lookup uses the token hash. Revocation and expiry checks happen before account data is returned.

### `device_challenges`

| Column | Purpose |
| --- | --- |
| `id` | Challenge identifier |
| `device_id` | Claimed device |
| `nonce_hash` | Hash of the random challenge nonce |
| `origin` | Origin bound into the challenge |
| `created_at` | Issue time |
| `expires_at` | Short expiry |
| `consumed_at` | One-time-use marker |
| `attempt_count` | Failed verification count |

Expired and consumed challenges are deleted promptly.

### `device_linking_otps`

| Column | Purpose |
| --- | --- |
| `id` | Device-linking OTP identifier |
| `user_id` | Target account |
| `issuing_device_id` | Active device that generated the OTP |
| `otp_hash` | Hash of the human-readable OTP |
| `status` | `active`, `expired`, or `consumed` |
| `attempt_count` | Failed redemption attempts |
| `created_at` | Creation time |
| `expires_at` | Ten-minute expiry |
| `consumed_at` | Successful redemption time |

OTP consumption and device insertion occur in one transaction or use a row lock so the same code cannot enroll twice. The submitted public key and proof of possession are validated during that transaction; neither belongs in the OTP record before redemption.

### `transfer_requests`

| Column | Purpose |
| --- | --- |
| `id` | Transfer identifier |
| `user_id` | Owning account |
| `sender_device_id` | Sender |
| `recipient_device_id` | Intended receiver |
| `protocol_version` | Negotiated protocol version |
| `status` | Transfer state |
| `created_at` | Offer time |
| `expires_at` | Offer expiry |
| `accepted_at` | Acceptance time, nullable |
| `completed_at` | Terminal time, nullable |
| `failure_code` | Bounded code, nullable |
| `relay_used` | Optional coarse operational flag |

This table does not store file names, MIME types, byte counts, SDP, ICE candidates, keys, or digests. The initial file metadata is forwarded to the intended recipient without durable storage. Terminal records are kept for 30 days.

### `websocket_tickets`

| Column | Purpose |
| --- | --- |
| `id` | Ticket identifier |
| `session_id` | Issuing session |
| `token_hash` | Hash of single-use random ticket |
| `created_at` | Issue time |
| `expires_at` | Short expiry |
| `consumed_at` | One-time-use marker |

### `security_events`

| Column | Purpose |
| --- | --- |
| `id` | Event identifier |
| `user_id` | Account when known, nullable |
| `device_id` | Device when known, nullable |
| `event_type` | Enumerated event |
| `outcome` | `success`, `failure`, or `blocked` |
| `network_fingerprint` | Rotatable HMAC of a normalized network identifier, nullable |
| `details` | Small allowlisted JSON object |
| `created_at` | Event time |
| `expires_at` | Retention deadline |

`details` rejects arbitrary strings. It must not contain email OTPs, email message bodies, IP addresses in plain form, tokens, keys, cookies, file metadata, SDP, or ICE candidates.

### `rate_limit_buckets`

Persistent rate limits use a bucket key derived with a server-side HMAC, a scope, counters, and an expiry. Raw emails, IP addresses, and session tokens are not used as primary keys. Short process-local limits may supplement this table but cannot replace account-wide limits.

## Indexes and constraints

The initial migration should include:

- unique index on `app_users.supabase_user_id`
- unique index on `app_users.email_normalized`
- unique index on `app_sessions.token_hash`
- unique account and fingerprint constraint for devices
- indexes on active device lookup by `user_id`
- indexes on session, challenge, device-linking OTP, ticket, and transfer expiry
- composite indexes for transfer ownership and device status
- foreign-key restrictions that prevent devices from different accounts appearing in one transfer
- check constraints for timestamps, counters, status values, and bounded lengths

## Retention

| Record | Retention |
| --- | --- |
| Active device | Until revocation or account deletion |
| Revoked device | Until account deletion, unless later policy shortens it |
| Active session | Until expiry, revocation, or account deletion |
| Expired or revoked session | Seven days for troubleshooting, then delete |
| Device challenge | Delete after expiry or consumption |
| Device-linking OTP record | Delete 24 hours after expiry or consumption |
| Transfer request | Delete 30 days after terminal state |
| Security event | Delete after 30 days |
| Rate-limit bucket | Delete after its enforcement window |

Cleanup runs in bounded batches so it cannot lock a large table. Account deletion cascades through application data after sessions and devices are revoked.

## Migrations and verification

Schema changes use Supabase migrations committed to the repository. Before a migration is accepted, tests apply it to an empty database and to the previous schema state. Database advisors and explicit privilege checks verify that no application table has become publicly accessible.
